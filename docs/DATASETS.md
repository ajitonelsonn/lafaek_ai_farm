# Datasets

Every dataset used to build Lafaek AI Farm, with its source, licence, size and
**what it does not cover**. The challenge scores that last column explicitly
(§7.2: *"You must also indicate what your data does not cover, and this is
scored"*), so the gaps are stated plainly rather than buried.

Nothing here was scraped. Every source is openly licensed and cited.

## 1. Vision model training data

All image data is pulled by scripts in `mobile-app/tools/cv/`, so the model is
reproducible from a clean checkout.

### 1.1 PlantVillage — maize and tomato

| | |
|---|---|
| **Source** | `leoho36/plant_village_dataset` on Hugging Face, from PlantVillage (Hughes & Salathé, 2015) |
| **Licence** | CC0 1.0 (public domain) |
| **Downloaded by** | `tools/cv/download_plantvillage.py` |
| **Used for** | `maize_healthy`, `maize_leaf_blight`, `maize_leaf_rust`, `maize_leaf_spot`, `tomato_healthy`, `tomato_leaf_problem` |
| **Volume** | ~400 images per class (tomato disease classes merged and halved to stay balanced) |

**What it does not cover.** These are **studio photographs: a single detached
leaf on a plain background, even lighting**. The challenge brief names this
exact weakness. A model trained only on PlantVillage performs noticeably worse
on a real field photo with soil, other leaves, shadow and motion blur in frame.
This is the single biggest limitation of the vision model and the reason for
the margin guard described in [ENGINEERING.md](ENGINEERING.md).

Source classes mapped:

```
Corn_(maize)___healthy                            -> maize_healthy
Corn_(maize)___Northern_Leaf_Blight               -> maize_leaf_blight
Corn_(maize)___Common_rust_                       -> maize_leaf_rust
Corn_(maize)___Cercospora_leaf_spot Gray_leaf_spot-> maize_leaf_spot
Tomato___healthy                                  -> tomato_healthy
Tomato___Early_blight | Late_blight | Septoria    -> tomato_leaf_problem
```

### 1.2 Rice disease dataset

| | |
|---|---|
| **Source** | `minhhungg/rice-disease-dataset` on Hugging Face |
| **Licence** | Apache-2.0 |
| **Downloaded by** | `tools/cv/download_rice.py` (Hugging Face datasets-server rows API) |
| **Used for** | `rice_healthy`, `rice_blast`, `rice_bacterial_blight`, `rice_brown_spot` |
| **Volume** | ~320 images per class |

Fetched through the rows API rather than cloning, which pulls ~1,300 images
instead of a 14 GB repository — the same constraint a farmer's connection
faces.

**What it does not cover.** A different source from PlantVillage, with
different cameras, backgrounds and colour balance. Mixing the two is what
caused the confident cross-dataset error documented in
[MODELS.md](MODELS.md): the first combined model learned *which dataset* an
image came from rather than what was on the leaf. Rice varieties are South-East
Asian but not specifically Timorese.

### 1.3 Papaya (pawpaw) leaf disease — Bangladesh

| | |
|---|---|
| **Source** | `Project-AgML/papaya_leaf_disease_classification_bangladesh` |
| **Licence** | CC BY 4.0 |
| **Downloaded by** | `tools/cv/download_papaya.py` |
| **Config** | `raw` (1,400 images). The `augmented` config was **not** used — augmentation happens during training, and duplicated images would inflate the validation score |
| **Used for** | `papaya_healthy`, `papaya_leaf_disease`, `papaya_pest` |

Six source classes collapse to three the app can give different advice for:

```
Healthy Leaf                 -> papaya_healthy
Leaf Curl, Mosaic, Ring Spot -> papaya_leaf_disease   (viral / disorder)
Mealybug, Mite Disease       -> papaya_pest           (visible pests)
```

Papaya was added because it grows in most Timorese house yards, so a farmer
can test the app on a plant they already have rather than taking it on trust.

**What it does not cover.** Photographed in **Bangladesh**, not Timor-Leste —
different varieties, soils and light. The healthy class has fewer images than
the disease classes (182 raw), so the others are capped to keep the classes
balanced rather than inflating healthy with duplicates. Papaya *fruit* and
*stem* problems are not covered at all; only leaves.

### 1.4 The `other` class — non-leaf photos

| | |
|---|---|
| **Source** | Generated from this project's own bundled illustrations and scene images |
| **Licence** | Project assets |
| **Used for** | `other` |
| **Volume** | 500 images, generated by `tools/cv/make_other.py` |

Exists so the model can say *"that is not a leaf"* instead of forcing every
photo into a disease class. A farmer who photographs the ground, their hand or
the sky gets an honest answer.

**What it does not cover.** Synthetic rather than a real distribution of
accidental photos.

## 2. Live data used at runtime

### 2.1 Open-Meteo — weather and soil moisture

| | |
|---|---|
| **Source** | https://open-meteo.com, `/v1/forecast` |
| **Licence** | Data CC BY 4.0; free tier is non-commercial |
| **API key** | None required |
| **Used for** | Current conditions, 8 hourly points, 7 daily points, `soil_moisture_3_to_9cm`, `precipitation_sum` |

Feeds the Home cards, the 7-day forecast, the rainfall chart and the inputs to
the rule-based risk engine. Cached in SQLite on arrival; see
[WEATHER_AND_MAPS.md](WEATHER_AND_MAPS.md).

**What it does not cover.** A global reanalysis/forecast model, not local
ground stations. It is interpolated to a coordinate, so a specific valley's
microclimate may differ. Soil moisture is modelled, not measured by a sensor
in the farmer's field.

### 2.2 OpenStreetMap — base map

| | |
|---|---|
| **Source** | `https://tile.openstreetmap.org` |
| **Licence** | Map data © OpenStreetMap contributors, ODbL — credited in the map corner |
| **Used for** | Pinning a field, showing the forecast point |

**What it does not cover.** Rural Timor-Leste is less completely mapped than
urban areas; field boundaries and minor tracks are often absent.

## 3. Knowledge library

| | |
|---|---|
| **Source** | Written for this project, in `mobile-app/assets/data/agriculture/*.json` |
| **Volume** | 49 articles: crops, diseases, pests, soil, irrigation, planting, climate, tips |
| **Used for** | TF-IDF retrieval, scan explanations, assistant answers when no language model is installed |

Compiled from general agronomic practice for South-East Asian smallholders.

**What it does not cover.** Not peer-reviewed, not endorsed by Timor-Leste's
Ministry of Agriculture, and **English only** — the interface is translated
into Tetun but these articles are not. Deliberately contains **no pesticide
dosages or product names**; it points to cultural and physical control first
and to an extension officer when a decision needs one.

## 4. Language models (downloaded by the farmer, not bundled)

| Model | Source | Licence | Size |
|---|---|---|---|
| Llama 3.2 1B Instruct Q4_K_M | `bartowski/Llama-3.2-1B-Instruct-GGUF` | Llama 3.2 Community Licence | 770 MB |
| Gemma 3 1B IT Q4_K_M | `ggml-org/gemma-3-1b-it-GGUF` | Gemma Terms of Use | 769 MB |

**What they do not cover.** General-purpose models with no agricultural
fine-tuning and **no meaningful Tetun ability**; they answer in English. They
are given retrieved knowledge articles as context rather than relied on for
facts. At 770 MB they are **too large to be called "small enough to send over
a weak connection"** — which is why the app is fully usable without them, with
the knowledge library answering instead.

### Claude Haiku (online enhancement)

| | |
|---|---|
| **Model** | `claude-haiku-4-5-20251001` via the Anthropic API |
| **Where** | FastAPI service on Amazon Lightsail — never in the APK |
| **Used for** | Second opinion on a local scan result, and advice for crops with no local model |

The phone sends the *local label, confidence, margin and farm context* — **not
the photograph**. Claude cannot see the image and is instructed never to
describe it.

## 6. Reproducing the training data

```bash
cd "Lafaek AI Farm/mobile-app/tools/cv"
python3 download_plantvillage.py 400   # maize + tomato  (CC0)
python3 download_rice.py               # rice            (Apache-2.0)
python3 download_papaya.py             # papaya          (CC BY 4.0)
python3 make_other.py                  # non-leaf class  (project assets)
python3 balance.py                     # cap classes to a common size
python3 train.py                       # trains, exports TFLite + model_meta.json
```

Class counts differ by source, so `balance.py` caps every class to a common
ceiling before training rather than letting the biggest class dominate the
loss. Surplus images move to `tools/cv/data_unused/` and are used as a
held-out check afterwards.

`train.py` writes `assets/models/crop_condition_mnv3s.tflite`,
`model_meta.json` and `labels.txt`. The app reads its class list from
`model_meta.json` at runtime, so adding a crop is a data task, not a code
change.
